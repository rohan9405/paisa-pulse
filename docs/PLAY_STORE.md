## Build setup

The existing direct SDK build now supports AAB through Google's bundletool; no Gradle migration or third-party app library was needed. APK compatibility checks remain in place.

Install JDK 17+, Android SDK build-tools 35.0.0 or newer, and **platforms;android-36** using Android SDK Manager. Configure `JAVA_HOME`, `ANDROID_BUILD_TOOLS` and `ANDROID_JAR` (absolute path to API 36 android.jar), or the git-ignored `android/local.json`. A project-local API 36 SDK in `android/.sdk/` is automatically preferred over the old local platform path.

Download official bundletool **1.18.3** from https://github.com/google/bundletool/releases/download/1.18.3/bundletool-all-1.18.3.jar to ignored `android/.tools/bundletool.jar`, or set `BUNDLETOOL_JAR`. Never commit tool binaries or private keys. Build-time Google font downloads may require network access; installed apps serve bundled fonts offline.

```sh
npm ci
npm run release:check
npm test
npm run test:e2e
npm run android:bundle
node scripts/play-assets.mjs
python3 scripts/verify-release.py
python3 scripts/package-release.py  # ZIP with builds and submission materials; no secrets
```

`android:bundle` builds both APK and AAB, signs them using the existing local keystore and verifies the pinned APK certificate, AAB signature and bundle structure. The keystore remains outside the repo in `~/.drip-private/` or `DRIP_PRIVATE_DIR`. No new signing key is created. Back it up offline.

`--skip-web` is for local rebuilds only: a fingerprint rejects stale web sources, version or config. The full command always rebuilds the UI. Local rebuilds may reuse the same build number, but **never upload a different artifact to Play with an already used build number**.

## Versioning and release flow

`package.json` is the single source: `version` is the user-visible version, `androidVersionCode` is the increasing Play build number. Build tools inject both into Android; Next.js reads the same version. The lockfile is updated by the bump command.

```sh
npm run release:bump -- patch  # fixes, e.g. 0.8.0 → 0.8.1; increments build
npm run release:bump -- minor  # a feature, e.g. 0.8.1 → 0.9.0
npm run release:bump -- major  # intentional major release, e.g. 1.0.0
```

Release deliberately: make changes → bump once → tests → signed bundle → internal testing → approve the same artifact → closed testing/production → staged rollout for updates. Keep a Git tag such as `v0.8.0` on the exact committed source used for a release, keep the `.aab`/metadata and add release notes. Do not tag unrelated or uncommitted source as a shipped release. No Git tag, push, GitHub release, Play API access or automatic production rollout has been created by this preparation.

Once Console and signing are configured, CI can build on a release tag and upload to internal testing using a restricted service account. Production promotion should stay an explicit choice. Do not put the signing key, passwords or service-account credentials in source. Separate upload-key configuration is an account setup step, not a reason to replace the installed app's signing key.

## Play Console steps still required

1. Complete identity verification, contact phone verification, and any requested real-device verification. The user's screenshot shows identity pending and phone verification waiting on it.
2. Resolve the Personal-account financial-app eligibility question with Play Developer Support; see the prepared question in `declarations.md`.
3. Create the app under the existing package. Enrol in Play App Signing using the **existing app signing key** so current sideload users can update compatibly. A Google-generated different key would break ordinary updates from current installations. Follow Console's supported encrypted key import, then configure a separate upload key if desired. Never upload a private keystore to the source repo.
4. Upload `drip.aab` to internal testing. Complete listing, privacy URL, rating, audience, App access, Financial features, Data safety and SMS permission declaration. Confirm the privacy contact mailbox is operational.
5. Record the native consent/import demonstration if requested. Confirm Cloudflare request logging/analytics before finalizing Data safety.
6. For this new Personal account, plan a closed test with at least **12 continuously opted-in testers for 14 days**, then apply for production access. This is separate from developer identity verification and SMS approval.
7. Use Play's pre-launch report, review crash/ANR findings, and submit for production review. First-time review/production access is not automatic after identity verification.

## Native/device release gate — not yet passed

No Android device was connected during preparation. Browser tests and compiled/bundle checks do not verify the Android permission dialogs or system UI. Before submitting, test on a dedicated phone/emulator (especially Android 16/API 36 and the minimum supported version):

- Fresh install: no SMS prompt; demo and manual tracking work without SMS permission.
- Disclosure → cancel and deny; later accept; verify SMS prompt ordering and no inbox import until accepted.
- Upgrade an existing signed v0.7.1 installation with a fictional transaction/backup; verify data and lock/widget settings survive. Update consent must not erase earlier data.
- Supported fictional bank SMS → one transaction; repeated sync doesn't duplicate; permission revoked → no further import; widget background behavior matches disclosure.
- Android 16 gesture navigation, Back from privacy/settings, keyboard, landscape and system bars; all important controls remain reachable.
- Backup export/restore and chosen cloud-folder behavior; biometric cancellation; widget privacy while locked.
- Test the bundle-generated APK, not just the standalone APK, and run Play's pre-launch report once uploads are available.
